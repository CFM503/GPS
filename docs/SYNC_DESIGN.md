# 数据同步与幂等性设计 (Sync & Idempotency Design)

## 1. 5 级优先级同步队列模型

车载巡查会产生海量结构化数据与大容量多媒体数据。在网络带宽有限或信号微弱的公路现场，**绝不能让几十兆的视频大文件阻塞核心路产数据的及时上报**。

系统构建了严格的 **5 级优先级同步队列 (`SyncQueueItem`)**：

```
[最高优先级 P1] 巡查会话摘要 (Session) ---------> 数据量 ~1KB，秒级入库，标记车辆出动与路段
       |
[次高优先级 P2] GPS 轨迹批次 (GPS Track) -------> 20点/批次，~3KB，支撑后台实时追踪与轨迹重现
       |
[业务核心 P3] 路产实体与视频事件 (Asset) -----> ~2KB，含道路桩号推算与视频帧秒数关联
       |
[多媒体轻量 P4] 现场实景照片 (Photo) ----------> ~500KB，路产特写与异常局部证据
       |
[大体量背景 P5] 视频切片分块 (Video Slice) -----> ~50MB/段，断点续传，后台静默流式上传
```

同步调度器按照 `priority ASC, created_at ASC` 取出待传输项。高优先级任务优先执行，若网络中断，已完成的 P1/P2/P3 已经安全进入服务端数据库，实现了“核心数据秒级报送、大媒体按需延后回传”。

## 2. 全链路客户端 UUID 与服务端幂等性保障

移动巡检在弱网重传场景下极易产生“网络超时未收到响应但服务端实际已写入”的状况。

### 核心规约：
1. **统一客户端 UUID**：
   - 客户端在离线状态下即使用 `crypto.randomUUID()` 生成唯一标识，作为该实体在本地与服务端的唯一业务主键。
   - 严禁“客户端生成一个 ID，上传到服务端后被丢弃并重新生成另一套自增 ID”。
2. **幂等性请求头 (`X-Idempotency-Key`)**：
   - 每次网络请求附带 `X-Idempotency-Key: {item_type}_{resource_id}`。
3. **服务端去重保护**：
   - 服务端若接收到已存在的主键 ID，判定为网络重传：
     - 不报错（不抛 500、不报主键唯一约束冲突）；
     - 更新属性或直接返回已有对象与 200/201 成功响应；
     - 巡查会话统计计数器（如 `asset_count`）仅在首次创建时累加，杜绝重复计数。
   - GPS 轨迹点批次根据 `(session_id, point_time)` 自动去重，杜绝重复轨迹折线。

## 3. 大文件视频切片断点续传协议

针对 50MB 录像切片，采用类似 TUS / RFC 流式分块协议：

1. **元数据初始化**：
   - 客户端调用 `POST /api/v1/videos/slices` 登记切片元数据（起止时间、文件大小）。
2. **查询已上传偏移量**：
   - 客户端调用 `POST /api/v1/videos/upload/init`，服务端检查临时文件 `.part` 的实际字节大小，返回 `uploadOffset`。
3. **流式追加上传**：
   - 客户端通过 `PATCH /api/v1/videos/upload/chunk?sliceId={id}` 从 `uploadOffset` 处发送分块数据，请求头携带 `Upload-Offset: {currentBytes}`。
   - 服务端以 Append 模式写入磁盘，返回最新 `Upload-Offset`。
4. **异常恢复**：
   - 若上传至 50% 突然断网，连接中断，临时文件保留已写入的 50%；
   - 网络恢复后，客户端调用 `init` 查询到已具备 50% 偏移，直接从后 50% 续传，节约 50% 重传流量。
5. **完整性落盘**：
   - 字节达到 `file_size_bytes` 时，服务端自动将 `.part` 临时文件原子重命名为 `.mp4` 正式文件，更新状态为 `COMPLETED`。
